# 05 复盘

## 1. 最难的问题

### 1.1 “时长”必须是工具说了算，且要能演示出修正

难点不在写循环，而在让“38 秒 → 修正 → 28 秒”这条链路**可复现**：

- 如果时长由模型自报，规则检查就形同虚设；所以时长只能来自 `estimate_duration`，
  且 `finalize_script` 会拒绝“没估算过”的稿子。
- 如果初稿本来就达标，就演示不出修正。解决方案是把 Mock 的初稿系数参数化：
  `01_normal` 用 0.98（一次通过），`05/06` 用 1.27（38 秒，必须修正）。
  这是刻意的实验设计，并在文档里写清楚了它是 Mock 参数、不是真实模型行为。
- 系数还踩过一个坑：按 1.38 计算应为 41 秒，原因是每镜时长会 `ceil` 到 0.1 秒，
  放大后总量超出预期。最终按公式反解到 1.27 才得到 38.0 秒。

### 1.2 防编造要“可执行”，而不是“提示模型别编”

只写“不要编造”是没有约束力的。最终落成三道闸门：
`submit_script` 查引用合法性 → `check_rules` 查断言与数字是否在原文 → `finalize_script` 拒绝未通过的稿。
调试中最典型的坑是**误伤**：产品型号 `S2` 被当成数据断言，导致正常稿被判违规。
修正方式是给数字加“量纲”约束，并把比对从子串改成带边界的正则。

### 1.3 框架与业务决策的边界

用 LangGraph 容易把业务分支写进条件边，那样就退化成“预设流程”。
本项目的做法是：条件边只判断三种情况——有动作、已结束、触顶兜底；
具体“压缩还是删镜”“换查询还是问用户”全部由模型输出与工具返回决定。

## 2. 学习收获

1. **状态机负责不跑飞，模型负责做选择**。把二者分开后，loop 的可控性和 ReAct 的灵活性可以同时拿到。
2. **工具返回值就是“提示词”**。`estimate_duration` 返回“超出 7.7 秒 + 每镜时长 + 语速”，
   模型才知道该压多少；返回一个裸数字，模型就只能瞎猜。
3. **trace 要在设计阶段定字段**，事后补是补不全的。本项目固定 7 个字段后，
   “决策依据/观察/下一步”可以直接被测试断言。
4. **可测的场景比漂亮的输出更有价值**。把“无素材”“工具失败”做成可注入的故障，
   比写十个正常用例更能暴露问题。
5. 规则检查的宽松与严格是个权衡：过严会误伤（型号数字），过松会放过编造（子串比对）。

## 4. 下一步

1. **用真实模型跑同一批用例**，对比它在“无素材”和“超时长”上的决策是否与 Mock 一致，
   并记录失败案例（这才是有价值的模型评测）。
2. **把事实校验从字符串包含升级为语义校验**：例如用抽取式相似度判断“原句是否真的支持改写后的话”。
3. **成本与延迟观测**：记录每步 token 与耗时，评估“多轮改稿”在真实模型下的性价比。
4. **接人工审核环节**：LangGraph 的 `interrupt` 天然适合“改稿后暂停等人确认”，
   这在团队协作里比全自动更有价值。
5. 把 `check` 子命令接进 CI，让创作者改稿后的每一次提交都自动跑时长与合规检查。
